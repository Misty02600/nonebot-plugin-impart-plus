# PLAN-0012：让 PK 结算原子提交

| 状态 | 最后更新 |
|---|---|
| 讨论中 | 2026-09-04 |

## 背景

当前 PK 在应用层依次调用多个 DataManager 方法，分别提交双方胜率、双方长度和双方挑战状态。任一数据库操作在中途失败，都可能留下只有一部分结果生效的对局。维护者要求记录并后续解决该数据一致性问题；本计划排在当前 XNN 雌堕功能之后，避免扩大正在设计的功能提交。

本计划只把一局 PK 的持久化结果收敛到一个数据库事务，不重新设计胜率、随机收益、挑战、冷却或文案。PLAN-0010 确定的 XNN 边界、零点保护和实际变化量将作为前置规则继续使用。

## 当前设计与缺陷

`GameApplication.execute_pk()` 完成场景、目标、初始化、同世界和冷却检查后生成胜负与成长随机数，随后按胜负路径依次执行：

1. 调整发起者胜率并提交；
2. 调整目标胜率并提交；
3. 调整发起者长度并提交；
4. 调整目标长度并提交；
5. 更新发起者挑战状态、长度和胜率并提交；
6. 更新目标挑战状态、长度和胜率并提交；
7. 再查询发起者最终胜率用于回复。

`DataManager.set_win_probability()`、`set_jj_length()` 和 `update_challenge_status()` 各自创建 Session 并提交。比如第三步写入发起者长度后第四步失败，用户会看到命令异常，但数据库中发起者已经获益、目标没有受损；重试命令还会再次抽取结果。当前没有事务回滚或补偿机制，架构文档已把它列为维护风险。

## 技术路线

### 单次事务拥有完整双方状态

- 在 core 中用一个纯结算结果表达双方最终长度、胜率、挑战状态、挑战事件、PLAN-0010 的实际基础变化量和 XNN 入场边沿；不包含 UserRef、Session 或回复文案。
- 应用层继续负责所有无副作用门禁、冷却和随机数生成，并保持现有随机调用顺序。随机值生成后调用一个聚焦的 DataManager PK 结算方法。
- DataManager 在一个 AsyncSession/事务中读取双方完整 `UserData`，调用 core 结算并写回两行，只执行一次 `commit()`；任何计算、flush 或 commit 异常都回滚双方全部变化。
- 双方用户已经由应用层初始化，事务中若任一行不存在则失败且不创建半局数据。事务使用数据库读到的当前值计算，避免继续通过嵌套 Session 读取旧值。
- 返回应用层的是已提交的类型化结算结果；Handler 沿用现有挑战和胜负文案，只改为读取实际基础变化量与显式 XNN 边沿。

### 保持的玩法和范围边界

- 胜负仍只用发起者当前 `win_probability` 与 `win_roll` 比较；胜者胜率 `-0.01`、败者 `+0.01`，不做双方归一化、阻尼、爆冷倍率或 xnn 胜率修正。
- 正值和负值仍只允许同世界 PK，成长/损失方向、挑战 25/30cm 状态机、称号和 5cm 惩罚保持 PLAN-0010 完成后的规则。
- 进程内 PK 冷却仍在进入数据库结算前记录；事务失败不会自动撤销冷却，避免把本计划扩展成内存状态与数据库之间的跨资源事务。后续如有真实运维问题再单独讨论。
- 本计划保证单局数据库写入全有或全无，不承诺解决两个进程同时操作同一用户的所有隔离级别问题，也不增加分布式锁或数据库后端专用语句。
- 不把透/榨、成长或场景开关一并纳入同一个通用 Unit of Work；互动雌堕继续使用 PLAN-0010 自己的聚焦事务。

### 实施步骤

| 顺序 | 改动 | 主要位置 | 预期结果 |
|---:|---|---|---|
| 1 | 提取完整 PK 纯结算 | `impart/core.py` 的 PK 与挑战规则 | 一个输入双方状态和随机值、输出双方最终状态的纯函数 |
| 2 | 增加原子数据方法 | `infra/data_manager.py` | 一个 Session 写回双方并只提交一次，异常自动回滚 |
| 3 | 收敛应用编排 | `impart/app.py::execute_pk()` | 删除六次独立写入和最终补查，返回已提交结果 |
| 4 | 适配 Handler 与测试 | `bot/handlers/game.py` 及现有 core/application/DataManager 测试 | 用户文案保持，实际变化量和挑战事件来自新结果 |
| 5 | 更新架构记录 | `docs/architecture/overview.md` | 移除 PK 部分提交风险，说明事务所有权 |

## 已确认事项

- 2026-09-04 · D-001：记录并后续修复 PK 多次提交造成的部分结算风险。
- 2026-09-04 · D-002：只原子化一局 PK 的数据库状态，不在本计划中重做胜率或其他玩法。
- 2026-09-04 · D-003：冷却保持现有数据库事务前记录和失败后不回滚的行为；不引入跨资源事务。
- 2026-09-04 · D-004：优先保证单进程默认数据库的一局全有或全无，不增加分布式锁或后端专用并发机制。

## 完成标准与验证

| 验收项 | 覆盖条件或输入 | 预期结果 | 验证方式 |
|---|---|---|---|
| 正值与负值正常结算 | 双方胜负、两个世界、挑战边界外 | 双方最终长度、胜率和实际变化量与改造前规则一致，只发生一次提交 | core 参数化测试与 application 回归 |
| 挑战组合 | 任一方开始、成功、失败或失去称号 | 双方挑战事件及额外长度/胜率变化与基础 PK 在同一事务提交，文案不重复计算 | 复用现有挑战与 PK Handler 聚合测试 |
| 故障回滚 | 写入两名用户后在 flush/commit 注入异常 | 双方长度、胜率和挑战字段全部保持结算前值，没有半局结果 | SQLite DataManager 聚焦测试 |
| 用户缺失 | 事务开始前删除任一参与者 | 结算失败且另一方不变化，不在数据层静默创建用户 | DataManager 聚焦测试 |
| 冷却边界 | 数据库结算失败 | 维持当前已记录冷却，不尝试跨资源补偿 | application 聚焦测试 |
| 非目标 | 并发多进程、胜率归一化、其他用例事务 | 不新增锁、配置或玩法变化 | diff 自检与现有回归测试 |
| 全量质量 | 完成实现后 | PK 外其他功能无计划外变化 | `uv run pytest`、Ruff lint/format、BasedPyright、`uv lock --check`、`uv build`、`git diff --check` |
