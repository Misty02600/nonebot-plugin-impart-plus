# PLAN-0010：实现 XNN 概率雌堕并合并查询

| 状态 | 最后更新 |
|---|---|
| 讨论中 | 2026-09-04 |

## 背景

当前正值用户可以经 PK 跨过零点直接进入负值世界，`0 < length <= 5` 又被拆成仅文案不同的 `XNN` 与 `NEAR_GIRL`，但注入量尚未参与状态变化。已经确认的目标是把雌堕设计为现阶段唯一的正转负玩法：`0 < length < 5` 的 XNN 在实际被透后，按当日总注入量逐次判定；未来负转正只通过完成深渊试炼后获得的“夺舍”能力实现，本计划不设计或实现夺舍。

本计划同时合并长度/深度查询与注入查询。默认 `银趴查询` 展示当前状态和当日注入量，`历史/全部` 选项继续提供历史总量与折线图，使 XNN 风险文案能够直接依据同一份查询结果生成。冷却默认值随新玩法节奏一并调整。

前置的 [PLAN-0011：移除不活跃惩罚机制](../done/PLAN-0011-remove-inactivity-penalty.md) 已完成，因此下文不再保留全局惩罚、活动时间或 APScheduler 相关分支。

前置的 [PLAN-0012：让 PK 结算原子提交](../done/PLAN-0012-atomic-pk-settlement.md) 已完成：application 级结算锁已经串行化单进程 PK 与成长状态写入，双方 PK 状态也会原子提交。本计划将在该边界上让雌堕复用同一临界区，并加入零点锁与 XNN 入场事件。

## 当前设计与缺陷

### 相关实现与当前行为

| 位置或符号 | 当前行为 |
|---|---|
| `impart/core.py::LengthState`、`classify_length()` | `1 < length <= 5` 为 `XNN`，`0 < length <= 1` 为 `NEAR_GIRL`；恰好 `5cm` 仍属于 XNN |
| `impart/core.py::evaluate_user_state()`、`resolve_interaction()` | `is_near_zero` 与 xnn 反透均使用 `0 < length <= 5`；没有统一的零点保护 |
| `impart/app.py::complete_interaction()` | 先生成 `1～100ml` 数量，再由 `DataManager.insert_ejaculation()`累计，之后单独读取当日总量；不检查接收者状态或雌堕 |
| `infra/data_manager.py::insert_ejaculation()` | 通过条件更新和冲突重试原子累计当日总量，但用户长度不在同一事务中更新 |
| `bot/matchers.py::IMPART_COMMAND`、`INJECTION_QUERY_COMMAND` | `银趴查询` 与 `注入查询/摄入查询/射入查询` 是两个独立命令和 matcher |
| `bot/handlers/game.py::queryjj()`、`bot/handlers/records.py::query_injection()` | 状态与注入量分别查询；前者区分 XNN/NEAR_GIRL，后者单独处理历史图表 |
| `config.py::Config` | 打胶、PK、嗦/舔、透/榨默认冷却分别为 300、60、300、3600 秒 |
| `infra/database.py::UserData.is_near_zero`、`is_zero_or_neg` | 保存上游用于抑制重复状态播报的派生标记，当前状态本身仍由长度决定 |

现有链路会造成三个直接问题：普通 PK 可以绕过雌堕切换世界；用户必须调用两个查询命令才能同时了解长度与风险进度；互动累计和未来转换若继续通过独立提交实现，并发时可能出现总量已经增加但长度尚未转换，或重复播报雌堕。

## 技术路线

### XNN 与世界边界

- 删除 `LengthState.NEAR_GIRL`，统一采用：`length >= 5` 为普通正值，`0 < length < 5` 为 XNN，`length <= 0` 为负值。称号的 `±30cm` 边界保持不变。
- 在 `impart/core.py` 只定义一份 `is_xnn(length)` 纯规则，供 `classify_length()`、反透、PK 状态边沿、查询和雌堕共同调用，避免五处分别维护 `< 5`。
- 查询中的 XNN 仍有两种文案，但这是依据当日注入量派生的展示，不再是独立长度状态：总量不超过 `200ml` 显示“已经是xnn啦”，总量超过 `200ml` 显示“快要变成女孩子啦”。
- `evaluate_user_state()` 删除原临界标记分支，`resolve_interaction()` 的 xnn 反透范围同步改为 `0 < length < 5`；恰好 `5cm` 不反透、不参与雌堕。
- 删除 `is_near_zero` 与同用途的 `is_zero_or_neg`，不再持久化可由长度变化推导的展示缓存。`jj_length` 始终是状态真值；PK 使用结算前后长度判断是否首次进入 XNN，雌堕使用明确事件结果判断正转负。
- 普通 PK 和挑战/称号惩罚通过一个 core 纯函数锁定原世界：按三位小数计算候选结果，正值跨线时返回 `0.001`，负值跨线时返回 `-0.001`。不在通用 DataManager 写方法中隐式钳制，以免妨碍旧库导入、测试夹具及雌堕等明确的绝对状态写入。打胶、开扣、嗦、舔继续沿远离零点的既有方向计算。只有本计划的雌堕，以及未来另行设计的夺舍，可以改变正负号。
- PK 跨入 XNN 时继续使用现有“变成xnn”提示；零点锁生效后，删除 PK Handler 中原有“变成女孩子”的跨零播报分支，避免保留与新世界转换规则冲突的死路径。
- PK 在 PLAN-0012 的原子结算中保留同一临界区内读取的双方结算前值、零点钳制后的基础结算值和挑战处理后的最终值。结果直接携带双方是否满足 `not is_xnn(before_pk) and is_xnn(final_length)`，Handler 只消费该布尔结果；停留在 XNN 时不重复提示，离开后再次进入仍可提示。
- 只有零点钳制实际发生时，基础胜负文案才使用结算前值与基础结算值之差显示真实变化量；普通未钳制路径继续使用现有随机增长/减少量。挑战失败或失去称号额外产生的 5cm 变化仍由挑战文案单独说明，避免重复计入。
- 自我成长和目标成长沿用 PLAN-0012 已接入的 application 结算锁；本计划只在临界区内增加新的世界与零点规则，不改变锁的作用域。
- `UserGameState` 与 `evaluate_user_state()` 删除两个展示字段及 `length_near_zero/length_zero_or_negative` 分支，继续只负责挑战、称号、长度惩罚和胜率状态。按现有状态机，可参与雌堕的有效 XNN 不会同时处于挑战或持有称号；本计划不为异常手工数据增加额外恢复分支。
- 保留 `is_challenging` 与 `challenge_completed`：同为 `27cm` 时，前者可表示胜率已乘 `0.8` 且成长受限的进行中挑战，后者可表示曾达到 `30cm`、仍持有称号的历史；这些语义不能仅由当前长度区分。等后续胜率模型重做时再讨论是否收敛挑战状态表示。

### 雌堕概率与判断顺序

每次互动仍先生成并累计原有 `1～100ml` 数量。只有本次 `InteractionResolution.action` 为 `INJECT`，且实际 `recipient` 在结算时满足 `0 < length < 5`，才使用包含本次数量的 `new_total` 抽取一次：

```python
probability = min(1.0, max(0.0, (new_total - 200) / 800))
feminized = roll < probability
```

- `200ml`、`1000ml` 和雌堕减去 `5cm` 属于玩法常量，集中放在 core，不增加部署配置项。
- `new_total <= 200` 时概率为 0，`new_total >= 1000` 时概率为 1；雌堕随机值使用结果范围为 `[0, 1)` 的 `random.random()`，因此两端分别必定不触发和必定触发。`min/max` 使独立的 core 概率函数对任意输入都保持 `0～1`。
- 每次符合条件的被透结算都重新抽取，不使用或保存隐藏耐受上限。假设用户持续保持 XNN 且每次实际被透，按当前 `1～100ml` 注入量模拟通常约在 `440ml`、第 8～9 次时触发；`1000ml` 是必定触发阈值，不是结算后总量上限，最后一次注入可以使总量越过该值。
- 主动命令名称不决定目标：正常透和反透都以领域结算中的实际动作、实际接收者为准。实际榨、查询、PK、成长和单纯进入 XNN 均不触发概率检查。
- 透与榨继续共用现有无类型当日总量：同一天此前由其他实际动作记入该用户的数量也参与概率计算，但只有当前结算的实际动作是透时才执行判定。
- 风险警告不持久化。只有实际接收者当时是 XNN，且一次被透使总量满足 `previous_total <= 200 < new_total` 时才有资格发送；若同一结算已经雌堕，最终文案覆盖警告。
- 警告属于本次回复中的瞬时事件；若消息发送失败，不补发也不另存状态。合并查询仍会依据当前总量显示“快要变成女孩子啦”，作为可重复查看的风险状态。
- 普通正值阶段跨过 200ml 不发送警告。此后跌入 XNN 时，查询可显示风险文案，下一次实际被透照常按当前总量抽取，但不会补发此前错过的一次性警告。
- 雌堕后的长度为 `round(current_length - 5, 3)`。原插件和当前插件的正常长度写入都保留三位小数；导入时又会把唯一可能的零值规范化为 `-0.001`，因此有效 XNN 范围实际为 `0.001～4.999cm`，转换结果自然位于 `-4.999～-0.001cm`，不再增加额外 `min/max`。
- 雌堕只把长度写入负值并通过本次类型化结果标记转换事件；胜率、挑战状态、当日总量与历史注入记录保持不变，不再写入 XNN 或负值缓存字段，也不添加成长减益、Buff、临时能力或女性反向转换。

### 事务与应用结果

- 用一个聚焦的数据方法替代 `insert_ejaculation()` 后再查询总量的组合调用。application 在原有本次注入量、耗时和雌堕随机值生成后取得共享结算锁；DataManager 随后在同一数据库事务中累计实际接收者的当日总量，并在命中时更新该用户长度。是否转换只通过返回结果传给应用层。
- 应用层在原有本次注入量和耗时随机值之后，为实际透调用一次 `random.random()`，再取得结算锁并把固定结果交给事务方法；同一条既有报告的数量和耗时顺序不变，实际榨不生成该随机值。infra 只调用 core 纯规则并持久化结果，core 返回是否跨过警告线、是否雌堕、转换前后长度和最终总量，不包含 NoneBot 对象或文案。
- 进程内互动冷却继续沿用现有职责；本计划保证的是“当日总量与雌堕长度转换”共同提交，不扩展为整个互动流程的分布式事务。
- 同一进程中的 PK、成长和互动结算共用一把短时锁；后到的互动只能在前一事务提交后读取状态，因此只有首个仍看到正值 XNN 的事务可以转换和播报，后续事务看到负值后只累计总量。互动中的目标选择、提示、头像读取和两秒等待均在锁外。
- 本计划实施时，PK 直接扩展作为前置完成的 PLAN-0012 原子结算，不重新引入 application 的多次提交；成长、互动和 PK 各自使用聚焦的数据方法，共享锁只协调单进程状态顺序，不变成通用 Unit of Work。

### 查询命令合并

`IMPART_COMMAND` 只使用两个同级子命令：`查询` 接收可选用户 At，较长的 `查询历史` 以 `查询全部` 为别名并接收同样的 At。较长子命令在前注册；该结构已在当前 Alconna 版本用真实 `UniMessage`/`At` 原型验证。根命令别名 `impart`、command start 和子命令前可省略空格的行为保持不变。公开命令收敛为：

- `银趴查询`、`impart查询`
- `银趴查询 @用户`
- `银趴查询历史`、`银趴查询全部`
- `银趴查询历史 @用户`、`银趴查询全部 @用户`

分别以 `history_query`、`query` 作为 dispatch 目标，同一个 Handler 处理两者；不支持 `银趴查询 @用户 历史` 等把历史标记放在 At 后面的排列。删除独立的 `INJECTION_QUERY_COMMAND`、`injection_query_matcher` 以及 `注入查询/摄入查询/射入查询` 入口，不保留 shortcut 或兼容 matcher。默认查询返回状态和当日总注入量；历史查询在同一结果上追加历史总量，至少两天记录时再附加原折线图。不存在的本人或目标继续遵循统一初始化规则：只创建并回复，不继续输出查询结果。

为避免把合并后的跨模块用例继续塞入较大的 `game.py`，将状态、当日总量和历史图表的接入逻辑集中到 `bot/handlers/query.py`；`records.py` 保留排行榜。应用层把 `query_user()` 与 `query_injection()` 收敛为一次场景检查和初始化，再由 DataManager 用一条查询取得用户状态及注入记录的一致快照；历史记录按 ISO 日期升序返回，供折线图按时间顺序绘制。

### 用户可见文案

正常透或反透的同一条最终回复仍先保留原互动报告，包括实际行动者、实际接收者、本次注入量和新的当日总量。只有随后发生的风险事件在报告文本后追加内容，不拆成两条消息。

首次跨过 200ml 且本次未雌堕：

> 由于{用户}的当日注入量过多，TA的{name}开始变得不稳定了...

触发雌堕：

> {用户}被注入了太多脱氧核糖核酸……
>
> 在{实际行动者}的猛烈攻势下，TA的{name}彻底萎缩消失了♡
>
> 取而代之的是一个深度{depth}cm的小学♡
>
> {用户}已经完全雌堕，变成女孩子了喵！

同一条事件文案只随机选择一次 `{name}`；`{用户}` 使用实际接收者的显示名和 ID，`{depth}` 为转换后长度绝对值。概率未命中时不增加“勉强撑住”或其他中间文案。

默认查询按本人/他人分别使用“你/TA”：

- 普通正值：`你的{name}目前长度为{length}cm喵`。
- XNN 且 `total <= 200`：`你已经是xnn啦！\n你的{name}目前长度为{length}cm喵`。
- XNN 且 `total > 200`：`你快要变成女孩子啦！\n你的{name}目前长度为{length}cm喵`。
- 负值：`你已经是女孩子啦！\n你的小学目前深度为{depth}cm喵`。
- 称号前缀继续保留；所有完成结果追加 `你当日总注入量为{total}ml`。历史选项再追加 `你历史总注入量为{history_total}ml`，他人查询替换为“TA”。

插件帮助增加：

> xnn在被透后，当日注入量达到200ml后有概率雌堕，注入量越多风险越高，达到1000ml时必定触发

### 冷却与文档

`Config` 的正式默认值改为：打胶 `600s`、嗦/舔 `600s`、透/榨 `1200s`、PK `600s`，README 只公布正式默认值。实施时在本工作树被忽略的 `.env.dev` 中把四项设为 `0`，并在不存在等价设置时由被忽略的 `.env` 选择 `ENVIRONMENT=dev`；已有本地配置只合并、不覆盖。这属于本地便利设置，不进入产品提交或完成标准。插件代码不根据环境自动清零，测试直接注入零冷却或控制时间。

同步 `PluginMetadata.usage`、README 和 `docs/architecture/overview.md` 的命令、状态、概率、查询及数据流说明。该阈值和玩法演进不单独创建 ADR。

- 2026-09-04 · D-008：原插件正常写入只保留三位小数，不会产生非零且绝对值小于 `0.001` 的状态；可能存在的 `0/-0.0` 只在上游导入时规范化为 `-0.001`。此后所有正常写入都维持非零不变量，core 和 PK 不为零值增加专门分支，也不兼容手工修改数据库等非支持输入。
