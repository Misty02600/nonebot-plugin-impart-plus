# PLAN-0017：一阶解锁双目标统一PK

| 状态 | 最后更新 |
|---|---|
| 已完成 | 2026-09-05 |

## 背景

用户在持续的一阶能力设计中明确新增：一阶后PK可以额外指定一个At用户，按一次胜率统一结算两个目标。即仍允许单挑，最多两个目标；一次判定胜负，发起者对两个目标同赢或同输，不是分别抽签。

本计划依赖 PLAN-0016 提供的 `challenge_tier`、个人基础增减×2和前后状态结算。双目标是独立能力，单列以便分别验证与提交，不重新打开×2决定。生产不需要先启用二阶，也不自动迁入旧 Memory Bank 的二阶「连击挑战」：旧稿独立判胜负、总收益上限均不是本轮已确认规则。

核查基线为 `feature@bef376b`；以下“当前设计与缺陷”记录实施前的基线事实，最终结果见“完成结果”。

## 当前设计与缺陷

路径相对 `src/nonebot_plugin_impart_plus/`。

| 位置 | 已核查的当前行为与影响 |
|---|---|
| `bot/matchers.py::PK_COMMAND` | 已使用 `Args["targets?", MultiVar(At)]` 接收多个At，保留 `pk/对决`、全局command start与同一个matcher即可，无需另建双目标命令。 |
| `bot/handlers/game.py::pk()` | 只把 `targets.result[0]` 转成Ref；其余At被忽略。需要按一阶能力选择实际使用的目标窗口。 |
| `impart/app.py::execute_pk()`、`_execute_pk()` | 仅接收一个目标，检查自己/世界/初始化后，记录一次冷却、抽一次胜负随机和基础数值，再调用数据层。新流程应校验全部选定参与者，不能为两个目标分别走该方法。 |
| `impart/core.py::resolve_pk_settlement()` | 计算一次双人PK并立即处理双方胜率和挑战；顺序调用两次会重复改变发起者属性，并使第一场后的阶级、减益影响第二场。 |
| `PkResolution`、`PkSettlement`、`impart/app.py::PkOutcome` | 当前是一份增减量、一个attacker和一个defender。多目标且目标倍率不同时，不能再把一份通用数字当每个人的真实变化。 |
| `infra/data_manager.py::settle_pk()` | 一个事务读取并提交两人。应扩成一次读取最多三人、一次完整提交；不能循环调用旧双人事务。 |
| `bot/handlers/shared.py::created_user_message()` | 只识别发起者与单个目标。双目标中第二名缺失用户也必须被正确表达，不能只初始化后遗漏提示。 |

## 技术路线

### 已确定的能力与边界

- 以开始结算时发起者的 `challenge_tier >= 1` 判断是否拥有双目标能力；同世界正负用户对称适用，进入更高阶挑战仍保留一阶能力。
- 一阶用户可以只At一人，也可以At两人；两个是上限，不是必须填满的数量。只有一个目标时仍按单挑，不补出第二人；两个目标共享一次胜负判定：只用本轮开始时发起者的有效胜率，不引入双方胜率归一化，也不按第一个目标结算后的胜率判第二人。
- 基础增减继续按每个人自己的开始阶级使用 PLAN-0016 的倍率，不把目标倍率乘到发起者身上。本轮通关不追溯增加可选目标，本轮掉阶不取消已经纳入结算的第二个目标。
- 按已确认的D-001共用一次基础随机量并按实际目标数累计份额；按D-002，每个参与者的胜率属性本场只变化一次。一次统一胜负不使发起者按目标数重复改变胜率。
- 全部参与者使用同一份开始快照；先计算每人的基础变化，发起者的所有份额先合计，再对每个人只执行一次挑战、称号与世界锁后处理。固定惩罚不按对手人数重复收取。
- 数据层将全部最终状态在一个事务中提交，失败全部回滚。继续共用现有单进程状态锁，网络资料查询和消息发送在锁外；消息失败不撤销或重放已提交的战斗。
- 不新增用户字段、冷却种类、逐次战斗记录表或通用技能框架。目标选择、冷却与初始化按已确认的D-003处理。

### 接入与结果结构

1. Handler保留同一命令注册，按D-003选择实际使用的At；其余命令的首At行为不变。未解锁时忽略第二At，不能提前构造或校验本来会被忽略的第二个Ref，避免未使用的角色At或身份错误阻断原单挑。
2. application在共享锁内最终核实能力、选定目标和参与者状态；只读资格准备不是授权快照，最终结算必须复核。若准备双目标后发起者已掉阶，整场拒绝，不降级为单挑，也不占用冷却或生成战斗随机。
3. 检查顺序沿用现有语义：场景关闭、缺目标、选中自己和非用户At等无需创建数据的拒绝在前；然后只为实际选定且去重后的参与者初始化缺失用户，有创建就提示并结束本次调用；只有所有人都存在时，才检查跨世界、冷却并生成战斗随机。例如正值A选择已存在的负值B和缺失C，第一次只创建C后结束，第二次才因B跨世界拒绝。
4. core扩展现有PK结算结果为一名发起者及有序目标结果集合，不另建一套重复的双人/三人引擎。身份关联留在application与数据层，core继续只处理领域状态。
5. 数据层复用现有批量读取、`_to_game_state()`、`_apply_game_state()`和单次事务方式，最多提交三个不同用户。
6. 回复沿用正负PK风格，明确列出发起者合计变化与每个目标的实际变化，各人的挑战/称号事件按发起者、目标At顺序追加；不能让双目标文案仍使用一个含糊的“对面”或共同增减数字。额外能力通知复用PLAN-0016已确认的D-004方案，在该通知中加入双目标PK说明，不再另发一条重复解锁消息；多人通关时分别通知真正通关的成员。

## 已确认事项

### D-001 · 已确认：双目标的基础量与发起者总收益/损失

2026-09-05，用户确认下述双目标数值方案。本轮共用一次 `get_random_num()`，每个目标各算一份原PK基础量；发起者合计实际目标的份额后再应用自己的×2。每个目标只结算自己的一份，并应用自己的倍率。

以基础量0.6、发起者有一阶、两个目标都无称号为例（不计固定惩罚和零点截断）：

| 统一胜负 | 发起者合计 | 目标A | 目标B |
|---|---|---|---|
| 发起者赢 | `(0.3+0.3)×2 = +1.2cm` | -0.6cm | -0.6cm |
| 发起者输 | `-(0.6+0.6)×2 = -2.4cm` | +0.3cm | +0.3cm |

双目标时发起者的总基础增减是已加成单挑的两倍，相对未加成单挑是四倍规模，不是四倍胜率。这是新增目标的额外效果，不重新否定已确认的一阶×2。

只选择一个目标时只算一份：同样基础量0.6、一阶发起者对无称号目标，发起者赢时+0.6cm、输时-1.2cm，不能因为拥有双目标能力就自动按两份计算。多目标仍先合计基础份额与个人倍率，再按既有精度舍入。

### D-002 · 已确认：每个参与者的胜率属性一场只改变一次

用户确认把统一胜负视为一场战斗：发起者的胜率只减/增0.01一次，每个不同目标也各增/减0.01一次；之后各自执行一次挑战进出带来的系数变化。胜率属性变化不乘个人数值倍率。

例如发起者以0.5胜率统一战胜两人后为0.49，而不是按目标数降到0.48。两个目标各自只增加0.01；统一失败时方向相反。

### D-003 · 已确认：按能力截取At窗口，去重不补位，无效目标整场拒绝

一阶允许一个或两个目标，不要求必须两个。无一阶只取第一个At；有一阶取实际提供的前至多两个At；多余At忽略。选定窗口内按用户身份去重、不从后面补位，重复同一用户只算一个目标、按单挑处理。因此 `@A @A @B` 只打A，B不补入。

- 无At仍在开关检查后回复既有缺目标文案。
- 选定的非用户At沿用 `user_at_target()` 跳过Handler的行为，不从后面捞用户替代；忽略窗口之外的At不作Ref转换。
- 选定目标中出现自己或跨世界者时整场拒绝，不先对合法目标结算。冷却和战斗随机在有效性检查之后；涉及缺失用户时仍只创建本次真正涉及的缺失者并提示，不进行战斗。
- 整场只检查并占用发起者的一次原PK冷却，目标不额外占用冷却。若资格预读后发起者在另一条操作中掉阶，最终锁内拒绝已准备的双目标战斗，不回退单挑。

未解锁时的第二目标和超过上限的At静默忽略，不额外回复能力不足；选定目标本身无效时沿用简短拒绝文案。忽略窗口之外的At不作Ref转换，也不创建用户。

## 完成结果

- Alconna命令仍接收多个At；Handler按发起者阶级截取前一或两个目标，在窗口内去重且不补位，窗口外目标不构造Ref。
- application在共享锁内复核双目标资格；缺失用户先初始化并返回，世界与资格等拒绝均发生在冷却和随机之前。
- core以一次胜负和一次基础量计算发起者及全部目标；每位参与者胜率只改变一次，个人倍率和挑战后处理也各执行一次。
- PK胜负直接保存在整场结果中，个人实际基础变化从参与者before/base计算，移除了独立`PkResolution`及并行数组拼接；单挑不再额外查询双目标资格。双目标测试使用10cm、tier0的有效普通目标并检查没有意外通关。
- DataManager用一个事务提交最多三名参与者；多人报告逐个显示目标及实际变化，正常一阶通关通知按发起者、目标顺序发送。
- 2026-09-05验证：`pytest` 161项通过，其中覆盖一阶双目标、单次随机/冷却、资格复核、缺失后跨世界、三人回滚、At窗口和多人报告；Ruff、BasedPyright、lock、build与diff检查通过。

## 自检结论

一次胜负、一阶可选一个或两个目标、数值份额、胜率变化次数与输入策略均已实现。单挑不会因拥有双目标能力而多算份额；目标因世界锁少损失时，延续当前PK规则，不反向减少发起者对应的完整收益份额。最多三人的统一事务和单次状态后处理防止部分提交与重复结算，没有顺序调用原单挑实现。本轮未执行Git提交。
